# llm-agent-harness

LLM 기반 에이전트/하네스 시스템을 구현해보는 개인 학습 프로젝트.
[toy-llm-project](../toy-llm-project)(트랜스포머를 밑바닥부터 구현)와는 목적이 다름 —
여기서는 **이미 있는 LLM을 "두뇌"로 가져다 쓰고, 그 주변에 도구 호출/검색/상태 관리 같은
"시스템"을 어떻게 쌓는지**를 배우는 게 목표로 시작했고, 진행하면서 "그냥 학습용을 넘어
실제로 쓸만한 것"을 만드는 쪽으로 방향이 넓어짐.

**주제**: "내 손안의 의사" — 증상/병명을 물어보면 위키피디아, 공식 질병정보(HIRA),
증상/원인/치료 정보(질병관리청), 관련 연구 논문(PubMed)까지 찾아서 답해주는 에이전트.

## 두 프로젝트 비교

| | toy-llm-project | llm-agent-harness (이 프로젝트) |
|---|---|---|
| 배우는 것 | 트랜스포머 내부 구조 (attention, 학습 루프 등) | 에이전트 구조 (도구 호출, 검색, 상태 관리) |
| LLM | 직접 만듦 (파라미터 9만개 미니 GPT) | 기존 오픈소스 모델을 가져다 씀 (Ollama) |
| 학습(훈련) 여부 | O (직접 학습시킴) | X (이미 학습된 모델을 호출만 함) |

## 실행 환경

- LLM: **Ollama**로 로컬에서 실행 (API 키/비용 불필요)
  - `llama3.2` (3B) — A단계 초기에 채팅 모델로 썼으나, 현재는 **실사용 코드에서 완전히
    은퇴함** (아래 "진행 기록" 참고)
  - `llama3.1` (8B) — 현재 유일한 채팅 모델. 도구 호출 판단, RAG 종합, PubMed 번역/종합
    전부 이걸로 처리
  - `bge-m3` (1.2GB) — 임베딩 모델 (다국어 지원). `nomic-embed-text`는 한국어 구분력이
    낮아서 교체함
  - 확인: `curl http://localhost:11434/api/version`
- 파이썬: conda base 환경 사용 (`/opt/anaconda3/bin/python`)
- API 키: `.env` 파일에 보관 (git에 안 올라감, `.gitignore` 처리됨)
  - `DISEASE_INFO_SERVICE_KEY`: 공공데이터포털 건강보험심사평가원 질병정보서비스
  - `KDCA_HEALTH_INFO_TOKEN`: 질병관리청 국가건강정보포털
- git: 로컬 저장소 + GitHub 비공개 저장소(`mylovepyd03/llm-agent-harness`) 연결됨

### 2026-09-18 (오전~밤) — C단계: 통합 + 결정론적 파이프라인
- `14_integrated_agent.py`로 A단계 도구 호출 + B단계 RAG 통합. RAG 도구는 이미
  완성된 답변을 주므로, 바깥쪽 LLM이 재해석하지 않고 그대로 반환하게 설계
  (재해석시키면 할루시네이션이 재발하는 걸 확인했었음)
- PubMed 번역/종합을 `llama3.1`(8B)로 교체 → 한자 섞임 없이 정확한 내용으로 개선됨을
  원문-번역-최종답변 3단 대조로 확인
- 멀티턴 대화(상태 기억) + `MedicalConversationState`(언급된 질환/증상을 구조화해서
  중복 없이 기록, 출처 추적) 구현. "요약해줘" 명령으로 LLM 없이 즉시 조회 가능
- **방향 전환**: 원래 "LLM이 스스로 도구를 계획"하게 하려 했으나, llama3.2가 도구
  선택 자체를 계속 실패해서 — **코드가 순서를 고정하는 결정론적 파이프라인**으로 전환
  (RAG 우선 → 실패시 위키피디아 → 공식코드 → "논문" 언급시 PubMed 추가). LLM은
  도구 "선택"에서 완전히 손을 뗌
- 자체 테스트로 발견·수정한 버그: 쿼리에 조사 붙어 엉뚱한 문서 검색, 무관한 질문에
  불친절한 오류, 복합 요청("설명+논문") 처리 실패, state 중복 기록, 답변이 질문을
  그대로 반복하는 습관
- 지칭어("그럼 치료법은?") 해결도 LLM 없이 `state.last_topic` + 마커 문자열로 구현

### 2026-09-18 (계속) — 품질 다듬기: llama3.2 완전 은퇴, 그리고 새로 발견한 문제들
- `search_symptom_info`의 답변이 가끔 "아증" 같은 존재하지 않는 단어를 만들어내는
  걸 발견 → 이 종합 단계도 `llama3.1`로 교체 → 확인해보니 **실제 활성 코드 경로에서
  llama3.2를 호출하는 곳이 한 곳도 안 남아있었음** (도구 선택은 파이프라인으로,
  종합은 하나씩 llama3.1로 넘어간 게 누적된 결과 — 의도한 단일 결정이 아니라
  여러 개별 수정이 겹친 결과임)
- 어투(캐주얼/정중체/짧은구어체/불안한말투/증상나열/캐주얼+아는병명) × 서로 다른
  증상 6개로 자체 테스트 → 5/6 완벽, 1개만 사소한 단어 하나 이상
- 사용자 피드백("답변이 짧고 딱딱함, 대화가 이어졌으면") 반영: 답변 톤을 친절하고
  상세하게, 답변 끝에 진단을 좁히는 후속 질문을 자동으로 붙이도록 프롬프트 보강.
  "네", "심해요" 같은 지칭어 없는 짧은 대답도 이어받도록 `state.awaiting_followup_reply`
  플래그 추가
- 참고자료를 글자 수(800자)로 자르다가 문장이 중간에 끊기고 LLM이 그 잘린 문장을
  그대로 베끼는 문제 발견 → `truncate_at_sentence()`로 문장 경계까지 포함하도록 수정
  (길이 제한보다 문장 완결성 우선)
- 답변을 길고 친절하게 바꾼 부작용으로 `num_predict=512` 한도에 걸려 문장이 끝에서
  잘리는 경우 다수 발견(6개 테스트 중 4개) → 1024로 상향해서 해결
- **후속 대화 중 검색 드리프트 버그 발견**: "기침 심함" → "네 심해요"로 이어지자
  검색어가 "기침 심함 네 심해요"로 합쳐지면서 엉뚱하게 "이물질에 의한 기도폐쇄
  응급처치(하임리히 요법)" 문서가 매칭됨 — 단순 기침 문의에 응급처치를 안내하는
  부적절한 답변 위험. **검색(임베딩 매칭)과 LLM에게 보여줄 질문을 분리**해서 해결
  (검색은 이전 주제만으로 안전하게, 질문에는 전체 맥락 포함)
- 문장 반복 감지 임계값을 3회→2회로 낮춤: "치료" 항목과 "예방" 항목에 완전히 똑같은
  문장이 정확히 2번만 반복되는 걸 놓친 사례 발견 → 기존 정상 답변들로 오탐 여부
  검사 후 안전하게 낮춤
- **약물명 지어내기 발견**: 반복 감지 임계값을 낮추고 재시도가 걸리자, 재시도된
  답변이 "브로몰라핀", "마스타인" 같은 **원문에 전혀 없는 가짜 약물 이름**을
  나열함 (원문 대조로 확인: 4개 약물명 전부 KDCA 원문에 없음). 프롬프트에
  "구체적인 약물 이름을 절대 나열/지어내지 말라"는 지시를 명시적으로 추가
- **검색 드리프트 재발 및 근본 수정**: 위 드리프트 수정 이후에도, 직전 답변이
  우연히 "?"로 안 끝난 경우(친절 프롬프트가 "항상 후속질문"을 지시해도 llama3.1이
  매번 지키진 않음) `awaiting_followup_reply`가 False가 되면서 "네 심해요"가 다시
  단독으로 검색돼 엉뚱한 문서(심장 질환)로 샌 것을 재발견. 순수 임베딩 점수로
  구분을 시도했으나 "네 심해요"(0.46)와 "그럼 치료법은?"(0.59) 둘 다 그 자체로도
  그럴듯하게 매칭돼 점수만으론 구분 불가 → **"짧은 문장인가"(8자 이하)**를 추가
  판단 기준으로 도입해서 마커/후속질문 플래그와 함께 OR로 결합, 재발 확인 후 해결

## 하네스가 방어하는 것들

LLM 혼자는 못 믿어서 코드로 감싼 부분들:
- 응답 시간/생성 길이 무제한 방지 (`timeout`, `num_predict`)
- 반복 루프(짧은 조각 반복 + 문장 반복 2회 이상) 감지 → 재시도(재시도 시 temperature를
  올려서 같은 결과가 반복되는 것 방지)
- 가짜 도구 호출(텍스트로 JSON 흉내, 백슬래시 섞임까지 포함) 감지
- 도구 인자 검증: 문자 화이트리스트(한자·키릴 등 낯선 문자 섞임) + **의미 검증**(KDCA
  임베딩과 비교해서 "문법은 맞지만 뜻 없는 문자열" 걸러냄)
- 도구 실행/검색 결과가 부실하면 LLM을 아예 다시 안 부르고 실패로 종료
- **도구 선택을 LLM 자유판단이 아니라 코드가 순서를 고정하는 파이프라인으로 결정**
  (RAG→위키피디아→공식코드→PubMed) — 소형 모델의 도구선택 불안정성을 구조적으로 우회
- 참고자료 문장 경계 유지(`truncate_at_sentence`) — 잘린 문장을 그대로 베끼는 것 방지
- 검색(임베딩 매칭)과 LLM 질문을 분리 — 후속 대화 내용이 검색 결과를 엉뚱하게
  끌고 가는 것 방지
- 구체적 약물명 등 "그럴듯한 세부사항 지어내기"를 프롬프트로 명시적 금지

## 알려진 한계

- 대화형 CLI(`14_integrated_agent.py`)는 Claude Code 채팅 환경 안에서 실시간 입력이
  안 됨 — 별도 macOS 터미널 앱에서 직접 실행해야 진짜 대화형으로 써짐
- PubMed 종합이 가끔 **실제 검색 안 된 가짜 인용문헌**을 만들어냄 (프롬프트로 완화만
  함, 근본 해결(인용 대조 검증)은 미완료)
- state에 병명을 못 찾은 경우 사용자의 원본 질문 문장이 그대로 "증상"으로 기록됨
  (사소한 지저분함)
- "위염"이 KDCA 611개 코퍼스에 없어서(API가 내용을 안 채워둔 13개 중 하나) 위염
  관련 질문은 "위십이지장 궤양" 등 유사 항목으로 대체 매칭됨 (방향은 맞지만 완전히
  정확하진 않음)
- 프롬프트로 "지어내지 말라"고 지시해도 완전히는 안 지켜지는 경우가 반복 관찰됨
  (가짜 인용문헌, 가짜 약물명 등) — 근본적으로는 규칙 기반 사후 검증이 필요하나
  아직 일반적인 "이 내용이 원문에 있는가" 검증 로직은 없음

## 진행 방식

- 한 번에 다 만들지 않고, 작은 단위로 쪼개서 구현 → 실행 결과 확인 → 다음 단계로
- 코드 쓰기 전에 개념 설명 먼저
- 버그/한계를 발견하면 숨기지 않고 실제 로그와 함께 보고 → 최소 범위로만 수정
- 재현 테스트로 고쳐졌는지 반드시 확인 (기존 정상 케이스가 깨지지 않았는지도 같이 확인)
