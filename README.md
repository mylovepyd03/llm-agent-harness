# llm-agent-harness

LLM 기반 에이전트/하네스 시스템을 구현해보는 개인 학습 프로젝트.
[toy-llm-project](../toy-llm-project)(트랜스포머를 밑바닥부터 구현)와는 목적이 다름 —
여기서는 **이미 있는 LLM을 "두뇌"로 가져다 쓰고, 그 주변에 도구 호출/검색/상태 관리 같은
"시스템"을 어떻게 쌓는지**를 배우는 게 목표로 시작했고, 진행하면서 "그냥 학습용을 넘어
실제로 쓸만한 것"을 만드는 쪽으로 방향이 넓어짐.

**주제**: "내 손안의 의사" — 증상/병명을 물어보면 위키피디아, 공식 질병정보(HIRA),
증상/원인/치료 정보(질병관리청), 관련 연구 논문(PubMed)까지 찾아서 답해주는 에이전트.

## 두 프로젝트 비교

| | toy-llm-project | llm-agent-harness (이 프로젝트) |
|---|---|---|
| 배우는 것 | 트랜스포머 내부 구조 (attention, 학습 루프 등) | 에이전트 구조 (도구 호출, 검색, 상태 관리) |
| LLM | 직접 만듦 (파라미터 9만개 미니 GPT) | 기존 오픈소스 모델을 가져다 씀 (Ollama) |
| 학습(훈련) 여부 | O (직접 학습시킴) | X (이미 학습된 모델을 호출만 함) |

## 실행 환경

- LLM: **Ollama**로 로컬에서 실행 (API 키/비용 불필요)
  - `llama3.2` (3B) — A단계 초기에 채팅 모델로 썼으나, 현재는 **실사용 코드에서 완전히
    은퇴함** (아래 "진행 기록" 참고)
  - `llama3.1` (8B) — 현재 유일한 채팅 모델. RAG 종합, PubMed 번역/종합/쉬운말
    재설명을 이걸로 처리 (도구 "선택"에는 LLM을 아예 안 씀 — 아래 "동작 흐름" 참고)
  - `bge-m3` (1.2GB) — 임베딩 모델 (다국어 지원). `nomic-embed-text`는 한국어 구분력이
    낮아서 교체함
  - 확인: `curl http://localhost:11434/api/version`
- 파이썬: conda base 환경 사용 (`/opt/anaconda3/bin/python`)
- API 키: `.env` 파일에 보관 (git에 안 올라감, `.gitignore` 처리됨)
  - `DISEASE_INFO_SERVICE_KEY`: 공공데이터포털 건강보험심사평가원 질병정보서비스
  - `KDCA_HEALTH_INFO_TOKEN`: 질병관리청 국가건강정보포털
- git: 로컬 저장소 + GitHub 비공개 저장소(`mylovepyd03/llm-agent-harness`) 연결됨

## 동작 흐름 (질문 하나가 들어왔을 때)

핵심 아이디어는 **"어떤 도구를 쓸지는 코드가 고정 순서로 정하고, LLM은 정해진
자리에서 검색된 근거를 문장으로 만드는 좁은 역할만 맡는다"**는 것. 원래는
"LLM이 스스로 도구를 계획해서 순서대로 호출"하게 만들려 했지만, 로컬 3B 모델
(llama3.2)이 도구 선택 자체를 계속 실패하는 걸 겪고 나서 지금 구조로 방향을
바꿨다. **이게 이 프로젝트 전체를 관통하는 결론이다: 소형 로컬 모델에는
"완전 자율 에이전트"보다 "결정론(코드) + LLM 하이브리드"가 훨씬 안정적이다.**

```
사용자 질문
   │
   ▼
main() 루프                          도구 호출 루프 진입 전 처리
   │  "종료/q" → 끝
   │  "요약/기록" → state.summary() 즉시 출력 (LLM 없이, 순수 텍스트 조립)
   ▼
run_agent_turn(messages, question, state)   ← 한 턴의 실제 시작
   │
   ├─ 1) 질의 해석 (resolve_query_with_context)
   │     - 문장에 KDCA 사전(624개) 병명이 그대로 들어있으면 문자열 검색으로
   │       바로 찾아낸다(known_term) — LLM에게 "병명이 뭐야?"라고 되묻지 않는다
   │     - 없으면 "그럼/그거" 같은 지칭어나, 직전 답변이 물음표로 끝났는지,
   │       또는 짧은 대답("네", "심해요")인지를 봐서 직전 주제를 이어붙일지 결정
   │     - 검색에 쓸 텍스트와 LLM에게 보여줄 질문 텍스트를 분리해서 반환
   │       (합쳐서 검색하면 "네 심해요" 같은 말이 검색을 엉뚱한 문서로 끌고
   │       가는 문제가 실제로 있었음)
   │
   ├─ 2) 건강정보 RAG 먼저 시도 (search_symptom_info) — 항상 1순위
   │     - bge-m3 임베딩으로 KDCA 문서 624개와 의미 유사도 계산 (LLM 아님, 순수
   │       벡터 수학) → 1등 유사도가 임계값(0.45) 미만이면 LLM도 안 부르고
   │       바로 "근거 부족"으로 처리
   │     - 임계값을 넘겨야만 llama3.1이 그 문서를 근거로 답을 생성 (문서에
   │       없는 내용은 지어내지 말라고 강하게 제약된 프롬프트)
   │
   ├─ 3) 실패하면 위키피디아로 대체 (search_wikipedia, LLM 없이 API 호출+파싱)
   │     — 이마저 실패하면 여기서 바로 안내 메시지로 답 종료
   │
   ├─ 4) 정확한 병명을 알아냈으면(known_term) 공식 코드 조회 추가
   │     (search_disease_code, 건강보험심사평가원 API, LLM 없음)
   │
   ├─ 5) 질문에 "논문/연구" 같은 표현이 있으면 PubMed 심층 검색 추가
   │     (search_pubmed_deep) — 이 도구 안에서만 LLM을 여러 번 씀:
   │       PubMed 검색(임베딩 재순위) → 논문별 번역(llama3.1) →
   │       종합(llama3.1, 답변에 나온 연도가 실제 검색된 논문 연도에 있는지
   │       대조해서 없으면 재시도) → 일반인용 쉬운 말 재설명(llama3.1, 실패/
   │       의심스러우면 전문용어 원문을 그대로 반환 — "이해하기 쉬움"보다
   │       "정확함"을 우선)
   │
   │  (2~5 전체가 예외 처리로 감싸져 있어서, Ollama/외부 API 중 하나라도
   │   장애가 나면 이번 턴만 롤백하고 친절한 메시지로 답한다 — 대화 세션
   │   전체가 죽지 않는다)
   │
   ├─ 6) state 기록 (MedicalConversationState, 전부 규칙 기반, LLM 없음)
   │     - 정확한 병명을 직접 언급했으면 → "질환"으로 기록
   │     - 증상을 서술해서 의미 검색으로 매칭됐으면 → 서술 자체는 "증상"으로,
   │       매칭된 병명은 "추정 질환"으로 같이 기록 → 여러 턴에 걸쳐 증상이
   │       쌓이고 같은 질환이 후보로 반복되면 자연스럽게 "문진처럼 좁혀지는"
   │       효과가 생긴다
   │
   └─ 7) 조각들을 합쳐 답변으로 반환, 다음 턴을 위해 상태 갱신
   ▼
messages(대화 원문)에 추가 → 화면에 출력
```

**LLM이 실제로 쓰이는 곳은 딱 세 군데뿐이다**: (1) 건강정보 RAG의 최종 답변 생성,
(2) PubMed 번역/종합/쉬운말 재설명, 그리고 그 각각에 대해 반복/낯선 문자 섞임
검증 + 재시도가 항상 따라붙는다. 그 외(도구 선택, 지칭어 해결, state 기록, 검색
자체)는 전부 코드로 결정된다 — "하네스가 방어하는 것들" 섹션 참고.

## 진행 기록 (시간순)

### 2026-09-15~16 — A단계: 기초 도구 호출 에이전트
- Ollama + llama3.2로 ReAct 패턴(도구 호출 → 실행 → 결과 반영 → 답변) 구현
- 도구 4개 순차 추가: 위키피디아 → 공식 병명/코드(HIRA) → 증상/원인/치료(KDCA) → PubMed
- 하네스 방어 로직 첫 도입: 반복 루프 감지, 가짜 tool_call 감지, 도구 인자 허용문자
  화이트리스트(한자·낱자모 섞이면 실패 처리), 근거 없으면 LLM 재호출 생략
- KDCA 국가건강정보포털 API 신청·연동 — 사용자가 포털에서 복사한 텍스트(600여 줄)를
  정규식으로 파싱해서 병명→콘텐츠번호 매핑 624개 구축
- `07_interactive_agent.py`로 대화형 CLI 완성 (단, Claude Code 채팅 환경 안에서는
  실시간 입력이 안 돼서 별도 터미널 앱에서 실행해야 함을 확인)

### 2026-09-17 — B단계: RAG, 그리고 첫 벽(PubMed 번역)
- KDCA 611개 질환 본문 수집 → 임베딩 시도 → `nomic-embed-text`가 한국어 구분을
  거의 못 하는 걸 발견(무관한 문서끼리 유사도 0.97+) → `bge-m3`로 교체해서 해결
- 증상 문장을 임베딩 검색으로 관련 질환에 매칭하는 RAG 완성 (`11_rag_agent.py`) —
  정확한 병명을 몰라도 검색되기 시작함
- PubMed 초록 기반 RAG 시도 → llama3.2:3b가 영→한 번역 시 한자/키릴 문자가 섞이는
  결함을 발견 → 검증 강화해도 6번 전부 실패해서 "답변 불가"로 안전하게 막는 데까지만
  확인하고 세션 종료 (다음 세션에 더 큰 모델 투입을 검토하기로 함)
- 이 시점에 "학습용을 넘어 제대로 만들어보고 싶다"는 방향 전환 언급됨

### 2026-09-18 (오전~밤) — C단계: 통합 + 결정론적 파이프라인
- `14_integrated_agent.py`로 A단계 도구 호출 + B단계 RAG 통합. RAG 도구는 이미
  완성된 답변을 주므로, 바깥쪽 LLM이 재해석하지 않고 그대로 반환하게 설계
  (재해석시키면 할루시네이션이 재발하는 걸 확인했었음)
- PubMed 번역/종합을 `llama3.1`(8B)로 교체 → 한자 섞임 없이 정확한 내용으로 개선됨을
  원문-번역-최종답변 3단 대조로 확인
- 멀티턴 대화(상태 기억) + `MedicalConversationState`(언급된 질환/증상을 구조화해서
  중복 없이 기록, 출처 추적) 구현. "요약해줘" 명령으로 LLM 없이 즉시 조회 가능
- **방향 전환**: 원래 "LLM이 스스로 도구를 계획"하게 하려 했으나, llama3.2가 도구
  선택 자체를 계속 실패해서 — **코드가 순서를 고정하는 결정론적 파이프라인**으로 전환
  (RAG 우선 → 실패시 위키피디아 → 공식코드 → "논문" 언급시 PubMed 추가). LLM은
  도구 "선택"에서 완전히 손을 뗌
- 자체 테스트로 발견·수정한 버그: 쿼리에 조사 붙어 엉뚱한 문서 검색, 무관한 질문에
  불친절한 오류, 복합 요청("설명+논문") 처리 실패, state 중복 기록, 답변이 질문을
  그대로 반복하는 습관
- 지칭어("그럼 치료법은?") 해결도 LLM 없이 `state.last_topic` + 마커 문자열로 구현

### 2026-09-18 (계속) — 품질 다듬기: llama3.2 완전 은퇴, 그리고 새로 발견한 문제들
- `search_symptom_info`의 답변이 가끔 "아증" 같은 존재하지 않는 단어를 만들어내는
  걸 발견 → 이 종합 단계도 `llama3.1`로 교체 → 확인해보니 **실제 활성 코드 경로에서
  llama3.2를 호출하는 곳이 한 곳도 안 남아있었음** (도구 선택은 파이프라인으로,
  종합은 하나씩 llama3.1로 넘어간 게 누적된 결과 — 의도한 단일 결정이 아니라
  여러 개별 수정이 겹친 결과임)
- 어투(캐주얼/정중체/짧은구어체/불안한말투/증상나열/캐주얼+아는병명) × 서로 다른
  증상 6개로 자체 테스트 → 5/6 완벽, 1개만 사소한 단어 하나 이상
- 사용자 피드백("답변이 짧고 딱딱함, 대화가 이어졌으면") 반영: 답변 톤을 친절하고
  상세하게, 답변 끝에 진단을 좁히는 후속 질문을 자동으로 붙이도록 프롬프트 보강.
  "네", "심해요" 같은 지칭어 없는 짧은 대답도 이어받도록 `state.awaiting_followup_reply`
  플래그 추가
- 참고자료를 글자 수(800자)로 자르다가 문장이 중간에 끊기고 LLM이 그 잘린 문장을
  그대로 베끼는 문제 발견 → `truncate_at_sentence()`로 문장 경계까지 포함하도록 수정
  (길이 제한보다 문장 완결성 우선)
- 답변을 길고 친절하게 바꾼 부작용으로 `num_predict=512` 한도에 걸려 문장이 끝에서
  잘리는 경우 다수 발견(6개 테스트 중 4개) → 1024로 상향해서 해결
- **후속 대화 중 검색 드리프트 버그 발견**: "기침 심함" → "네 심해요"로 이어지자
  검색어가 "기침 심함 네 심해요"로 합쳐지면서 엉뚱하게 "이물질에 의한 기도폐쇄
  응급처치(하임리히 요법)" 문서가 매칭됨 — 단순 기침 문의에 응급처치를 안내하는
  부적절한 답변 위험. **검색(임베딩 매칭)과 LLM에게 보여줄 질문을 분리**해서 해결
  (검색은 이전 주제만으로 안전하게, 질문에는 전체 맥락 포함)

  fuzzy 매칭되는 걸 발견 - 위키피디아 검색 API는 KDCA 임베딩 검색과 달리 "이
  결과가 실제로 관련 있는가"를 알려주는 점수가 없음. `search_wikipedia()`에서
  문서를 찾아온 뒤 우리 자신의 bge-m3 임베딩으로 질문과 본문의 유사도를 다시
  검증하도록 추가(`MIN_SIMILARITY_WIKIPEDIA = 0.4`) - 실측: 무관한 오검색
  0.17~0.28 vs 진짜 관련 있는 검색 0.53~0.71로 KDCA 때보다 훨씬 깨끗하게 갈림.
  이 과정에서 **부수 발견**: 위키피디아의 "검색 결과 없음" 메시지를
  `_is_failure_message()`가 애초에 실패로 인식을 못 하고 있었던(문구가 "찾지
  못"/"답변할 수 없습니다"/"설정되지 않았습니다" 중 어느 것도 안 걸림) 잠재
  버그도 같이 발견해서 문구 체크 추가
- 최종 확인: KDCA도 실패 + 위키피디아도 관련성 검증에서 걸러지면, 이제
  "이 질문은 제가 다루는 건강/의료 정보 범위를 벗어났거나..." 라는 정직한
  안내로 끝남(엉뚱한 인물/질환을 답이라고 우기지 않음). "위염이 뭐야?" 같은
  기존 정상 케이스는 회귀 없이 그대로 동작하는 것도 재확인

### 2026-09-24 — 같은 예시로 재검증하다 추가로 발견한 버그 3개
사용자가 "주사피부염일때 어떻게 해야해?"(어제와 살짝 다른 말투)로 다시
테스트해달라고 함 - "말투 자체에 집착하지 말고, 병명이 중요하다. 건강정보포털에
없으면 위키피디아(병명만) 또는 PubMed로 가야 한다"는 방향 제시를 받고 순서대로
고침.
- **조사 정리 규칙 확장**: "일때"("~일 때"의 붙여쓰기)가 기존 조사 목록에
  없어서 못 걸러짐 → `clean_disease_query`의 정리 규칙에 "일때/을때/할때",
  "이라면/이었으면", "이고/이지만/이라도", "일까(요)/인가(요)" 등 흔한 연결어미
  묶음을 추가
- **PubMed를 최종 폴백으로 추가**: 지금까지 PubMed는 "정확한 병명을 알고 있고
  + '논문' 언급"할 때만 덧붙이는 용도였는데, 그러면 KDCA/위키피디아 둘 다 없는
  병명은 PubMed를 아예 못 씀. `run_agent_turn`에서 위키피디아까지 실패하면
  정리된 병명 후보로 PubMed를 마지막으로 시도하도록 배선 추가
- **PubMed 영문 변환에 LLM 폴백 추가**: `_to_english_query`가 HIRA 공식 DB에
  없는 병명은 한글 그대로 PubMed에 넘기고 있었음 → 실측해보니 한글 그대로는
  검색 결과 0건, 올바른 영어(rosacea)로는 5건 나오는 걸 확인 → HIRA 조회
  실패 시 llama3.1에게 영어 병명을 추정 번역시키는 `_translate_term_to_english`
  추가
- **`_is_failure_message` 놓친 문구 재발견**: 이번엔 `search_symptom_info`가
  모델 생성에 계속 실패했을 때 쓰는 "[오류] 모델이 계속 비정상적인 응답을 내서
  포기했습니다"가 실패로 인식이 안 돼서 그대로 최종 답변에 샐 뻔한 걸 발견
  (지난번 위키피디아 실패 메시지 때와 같은 종류의 버그가 또 발생) → 이번엔
  개별 문구를 계속 추가하는 대신 **"[오류]" 접두사 체크**를 넣어서 앞으로
  새 오류 메시지가 추가돼도 이 접두사만 지키면 자동으로 잡히게 일반화
- **아직 못 푼 진짜 어려운 케이스**: PubMed 폴백까지 갔을 때, LLM이 "주사"를
  "주사기(injection)"로 오역해서 "Intramuscular panniculitis"(전혀 다른
  질환)로 번역해버림 - "주사"가 "주사기"와 "로사시아를 가리키는 옛 한자어"
  두 뜻을 가진 진짜 어휘 중의성 문제라서, 문턱값 조정 같은 방법으로는 해결이
  안 됨. 알려진 한계로 기록만 해둠
- 여러 번 재현했을 때 비결정성 때문에 KDCA가 애매하게 통과(오답)하거나 실패해서
  위키피디아로 넘어가는(일반적이지만 관련 있는 "피부염") 두 가지 경로가 다
  나왔지만, 두 경우 다 예전처럼 완전히 무관한 답("나혜석", "사시")은 더 이상
  안 나오는 것을 확인

## 하네스가 방어하는 것들

LLM 혼자는 못 믿어서 코드로 감싼 부분들 (도구 선택이 결정론적 파이프라인으로
바뀌면서, LLM에게 도구 호출을 직접 맡기던 시절의 방어 로직 — 가짜 tool_call
감지, 도구 인자 문자/의미 검증 — 은 더 이상 필요 없어져서 삭제함, 2026-09-22):
- 응답 시간/생성 길이 무제한 방지 (`timeout`, `num_predict`)
- 반복 루프(짧은 조각 반복 + 문장 반복 2회 이상) 감지 → 재시도(재시도 시 temperature를
  올려서 같은 결과가 반복되는 것 방지)
- 도구 실행/검색 결과가 부실하면 LLM을 아예 다시 안 부르고 실패로 종료
- **도구 선택을 LLM 자유판단이 아니라 코드가 순서를 고정하는 파이프라인으로 결정**
  (RAG→위키피디아→공식코드→PubMed) — 소형 모델의 도구선택 불안정성을 구조적으로 우회
- 참고자료 문장 경계 유지(`truncate_at_sentence`) — 잘린 문장을 그대로 베끼는 것 방지
- 검색(임베딩 매칭)과 LLM 질문을 분리 — 후속 대화 내용이 검색 결과를 엉뚱하게
  끌고 가는 것 방지
- 구체적 약물명 등 "그럴듯한 세부사항 지어내기"를 프롬프트로 명시적 금지
- PubMed 종합 답변에 등장하는 연도를 실제 검색된 논문 연도와 대조(`_has_fabricated_citation`)
  → 실제 없는 연도를 인용하면 재시도, 그래도 안 되면 실패로 안전하게 종료
- state에 병명을 기록할 때 사용자의 원본 질문이 아니라 RAG/위키피디아가 실제로
  매칭한 병명을 기록 (질문 문장 그대로 "증상"으로 오염되는 것 방지)
- PubMed 답변을 일반인이 이해하기 쉽게 재설명하되(`_simplify_for_layperson`),
  실패/의심(연도 조작·과도한 길이 증가)이면 전문용어 원문을 그대로 반환해서
  "이해하기 쉬움보다 정확함"을 우선
- **외부 서비스 장애 대응**: Ollama/위키피디아/KDCA/PubMed 중 하나라도 네트워크
  예외를 던지면 `run_agent_turn`이 이번 턴에서 건드린 것(방금 넣은 user 메시지,
  turn 카운트)을 롤백하고 친절한 안내 메시지로 답함 — 대화 세션 전체가 죽지 않게
  방지. `main()`에도 예상 못 한 다른 예외까지 한 번 더 막는 안전망이 있음
- KDCA 매칭 임계값을 0.6으로 올려서, 애매하게만 관련 있는 문서를 확신에 찬
  근거로 쓰는 것 방지 (약해도 넘어가던 예전 임계값 0.45에서 상향)
- 코퍼스에 없는 단어로 위키피디아 폴백을 탈 때, 문장 전체가 아니라 조사/어미를
  정리한 병명 후보만 검색어로 사용 (`clean_disease_query`)
- **위키피디아 검색 결과 자체도 관련성 재검증**: 문서를 찾아와도 우리 자신의
  임베딩으로 질문과 본문이 실제로 관련 있는지 확인하고, 무관하면(유사도 0.4
  미만) "결과 없음"으로 처리 — 위키피디아 검색 엔진이 오타/낯선 표기에 fuzzy
  매칭으로 완전히 무관한 문서를 찾아오는 것을 막음
- KDCA/위키피디아 둘 다 실패하면 PubMed를 마지막 폴백으로 시도, HIRA 공식 DB에
  없는 병명은 llama3.1로 영문 번역을 추정해서 검색 (`_translate_term_to_english`)
- 새 실패 메시지를 깜빡 놓치는 걸 방지하려고 `_is_failure_message`가 "[오류]"
  접두사를 공통 규칙으로 인식 (개별 문구를 하나씩 추가하는 대신 일반화)

## 알려진 한계

- 대화형 CLI(`14_integrated_agent.py`)는 Claude Code 채팅 환경 안에서 실시간 입력이
  안 됨 — 별도 macOS 터미널 앱에서 직접 실행해야 진짜 대화형으로 써짐
- 프롬프트로 "지어내지 말라"고 지시해도 완전히는 안 지켜지는 경우가 반복 관찰됨
  (가짜 인용문헌, 가짜 약물명, 무관한 용어 섞임 등) — PubMed 연도 인용은 규칙
  기반 검증을 추가했지만, 이건 "연도"라는 좁은 형태만 잡아내는 것이라 다른 형태의
  지어내기까지 막는 일반적인 "이 내용이 원문에 있는가" 검증은 아직 없음
- **미해결 버그(원인 미확정)**: "천식" PubMed 답변에 무관한 "동맥경화"가 섞인 사례
  1건 발견. 계측 스크립트로 동일 쿼리를 5회 재현 시도했으나 재현 안 됨 →
  temperature=0에서도 llama3.1 번역/종합 출력이 실행마다 달라지는 것(번역 성공/실패
  여부부터 매번 다름)을 확인했지만, "동맥경화"가 synthesize 단계와 simplify 단계 중
  어디서 처음 생겼는지는 로그 근거로 확정하지 못함. `search_pubmed_deep`에 단계별
  원문을 상시 `data/pubmed_debug_log.jsonl`에 남기는 로깅을 추가해뒀으니, 재발하면
  로그 대조로 바로 잡을 것
- 일부 PubMed 논문은 번역 검증 실패로 통째로 스킵됨 (정보 손실, 안전하게 건너뛰긴 함)
- **어휘 중의성 오번역**: PubMed용 한→영 번역(`_translate_term_to_english`)이
  "주사"(주사기 vs 로사시아를 가리키는 옛 한자어)처럼 뜻이 여러 개인 단어를
  잘못된 뜻으로 번역해서 완전히 다른 주제의 논문을 확신 있게 찾아오는 사례
  발견("주사피부염" → "Intramuscular panniculitis"로 오역). 문턱값/검증
  방식으로는 해결이 안 되는 진짜 어휘 중의성 문제라 아직 미해결

## 진행 방식

- 한 번에 다 만들지 않고, 작은 단위로 쪼개서 구현 → 실행 결과 확인 → 다음 단계로
- 코드 쓰기 전에 개념 설명 먼저
- 버그/한계를 발견하면 숨기지 않고 실제 로그와 함께 보고 → 최소 범위로만 수정
- 재현 테스트로 고쳐졌는지 반드시 확인 (기존 정상 케이스가 깨지지 않았는지도 같이 확인)
